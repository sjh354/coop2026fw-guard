## 변형 4종 생성 (150행 완성)

우회표기·띄어쓰기는 프로그램으로 생성했다. 각 base 문장에서 타겟 단어(욕설/슬러 또는 safe 문장의
핵심 단어) 하나를 지정하고, 유니코드 한글 분해 공식으로 자모 단위 분리(우회표기, 예: "새끼"→
"ㅅㅐㄲㅣ")와 음절 사이 공백 삽입(띄어쓰기, 예: "새끼"→"새 끼")을 적용했다 — 손으로 하면 30개
전부 일관성을 맞추기 어려워서 스크립트로 처리, 대신 타겟 단어가 문장에 실제로 존재하는지
`assert`로 검증했다.

번역투·code-switching은 의미 보존이 핵심이라 30개씩 직접 작성했다. 번역투는 원문/직역체 표현
(그녀들은/그들은 + ~것이다/~것으로 보인다 식 문어체)으로, code-switching은 자연스러운 한영 혼용
(단어 단위 영어 치환, 예: "정신나간"→"crazy", "나라"→"country")으로 썼다.

`data/ko_probe.csv` 최종 150행 (base 30 × variant 5종) 완성. `csv.DictReader`로 재검증:
variant_type별 정확히 30행씩, label은 harmful 100 / unharmful 50 (base 20/10의 5배), 빈 필드 없음.

## eval.py에 --ko-probe 모드 추가, 서버 실행

`eval.py`는 원래 PGPrompts(HF 데이터셋)만 읽게 짜여 있어서 `data/ko_probe.csv`를 읽고
`results/ko_probe_{model}.csv`로 저장하는 `--ko-probe` 플래그를 추가했다. CLAUDE.md가 최상위
코드 파일 개수를 늘리지 말라고 못박아둬서 새 스크립트 대신 `eval.py`에 모드를 얹는 방식을 택함.
flip rate는 각 base_id의 "원문" 예측을 기준으로 나머지 4개 variant의 예측이 달라진 비율로 계산.

SGuard-v1은 아직 `models.py`에 프롬프트 빌드/파싱 로직이 없어서(Phase 1 모델 카드 리딩 blocker)
이번 실행에서는 제외 — PolyGuard, LlamaGuard3-1B 2개만 먼저 돌렸다.

로컬에서 커밋 → push, 서버(`172.10.5.23`)에서 `git pull` → `guard` env 활성화 → 두 모델 순서로
`python eval.py --model {polyguard,llamaguard} --ko-probe` 실행. 디스크 25GB 여유, GPU 메모리
비어있는 것 확인 후 진행.

**결과 (parse 실패율 둘 다 0%)**

| variant_type | PolyGuard flip rate | LlamaGuard3-1B flip rate |
|---|---|---|
| 우회표기 | 23.3% | 6.7% |
| 띄어쓰기 | 10.0% | 6.7% |
| 번역투 | 26.7% | 10.0% |
| code-switching | 13.3% | 10.0% |

두 모델 다 **번역투**(학습 분포 이탈 노리는 변형)에서 flip이 가장 잦다. PolyGuard가 LG3-1B보다
전반적으로 flip rate가 2~4배 높은 것도 눈에 띄는데, 이게 PolyGuard가 더 예민한 건지 아니면 원래
경계선에 가까운 판정을 많이 해서인지는 Phase 6에서 원문 예측 자체의 confidence/margin을 봐야
판단할 수 있을 것 같다.

서버에서 결과 커밋·push, 로컬 `git pull`로 동기화 완료. `README.md`/`docs/PLAN.md`도 같이 갱신.
