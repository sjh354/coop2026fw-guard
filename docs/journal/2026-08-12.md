## EXP-1: Latency 벤치마크

`docs/NEW_PLAN.md`에 잔여 실험 5건(EXP-1~5)을 정리해뒀고, 그중 EXP-1(latency)부터 착수했다.
NEW_PLAN.md 자체도 아직 커밋 안 된 상태였어서 같이 커밋했다.

**설계**: ko_probe 원문(variant_type=="원문") 30문장 + PGPrompts en 20문장(`results/llamaguard_en.csv`
첫 20행, 기존 평가에서 쓴 데이터셋 순서 그대로 재사용) = 50건 고정 세트를 `exp/latency_inputs.json`에
저장. 모델당 warmup 5회(측정 제외) 후 batch=1로 순차 측정. `torch.cuda.synchronize()`를 tokenize/
generate 각 구간 전후에 호출해서 비동기 커널로 인한 왜곡을 막았다. 모델 전환 시 `del model` +
`torch.cuda.empty_cache()`.

**구현 이슈**: `python exp/latency_bench.py`로 실행하면 `sys.path[0]`이 `exp/`가 되어 루트의
`models.py`를 못 찾는다(`ModuleNotFoundError: No module named 'models'`). `PYTHONPATH=.`을 붙여서
해결 — 서버에서 이 스크립트를 다시 실행할 일이 있으면 반드시 `PYTHONPATH=. python exp/latency_bench.py`
형태로 실행할 것.

**결과** (`results/final/latency_raw.csv`, `latency_summary.csv`):

| model | median_ms | p95_ms | mean_output_tokens | ms_per_output_token |
|---|---|---|---|---|
| llamaguard | 46.6 | 89.4 | 3.18 | 15.5 |
| polyguard | 677.2 | 722.2 | 31.6 | 21.8 |
| sguard | 297.7 | 299.3 | 5.0 | 59.6 |

절대 latency는 LG3-1B가 압도적으로 빠르지만, 이는 출력 토큰 수가 짧기 때문(safe/unsafe 한 줄).
토큰당 정규화(`ms_per_output_token`)로 보면 SGuard가 가장 느리다(5토큰짜리 카테고리 생성인데도
스텝당 비용이 큼 — 2B 파라미터 규모 때문으로 추정, 별도 분석은 안 함). p95가 median 대비 크게
튀는 모델은 LG3-1B(46.6 → 89.4ms, 약 2배) — 일부 입력에서 unsafe 판정 시 카테고리 코드까지
생성하느라 출력 토큰 수가 늘어난 결과로 보인다(raw CSV의 output_len_tokens로 확인 가능).

**다음**: EXP-2(response harmfulness 재현) 착수 예정.

## EXP-2: Response Harmfulness 재현

**계획 수정 발견**: NEW_PLAN.md는 "PolyGuard는 재실행 불필요, 기존 4-field raw 출력에서 파싱만
추가"라고 가정했는데, 기존 `results/polyguard_{lang}.csv`/`results/sguard_{lang}.csv`를 열어보니
전부 `response=""`로 실행된 것이었다(eval.py의 `run_eval`이 애초에 prompt만 넘김). 즉 기존
raw_output의 "Harmful response" 필드는 빈 응답에 대한 판정이라 이번 실험에 못 쓴다. 사용자에게
보고하고 3모델 전부 재실행으로 계획을 수정했다(승인받음).

**판단 근거 확보 (스모크 테스트)**:
- PGPrompts 데이터셋 필드 확인: `response`(실제 응답 텍스트), `response_harm_label`(정답,
  harmful/unharmful). en/ko 각 1699건(prompt_harm_label 있는 것) 중 `response_harm_label=None`
  10건 제외, 빈 문자열 response는 0건.
- LG3-1B: chat template에 user+assistant 두 턴을 넣으면 "Task: Check ... in 'Agent' messages"로
  자동 전환되는 걸 실제 출력으로 확인 — 별도 프롬프트 포맷 불필요, 기존 safe/unsafe 첫 줄 파서
  그대로 재사용 가능.
- PolyGuard: raw_output에 이미 "Harmful response: yes/no" 필드 있어 정규식 파서만 추가
  (`models.parse_response_harm`).
- SGuard: 모델 카드 예제(`{"role":"user","prompt":...,"response":...}`)가 `models.py`에 이미
  구현돼 있어 response만 채우면 됨. 단 일반 `tok.decode()`로 스모크했더니 빈 문자열이 나와서
  당황했는데, SGuard는 5개 카테고리를 special token logit 비교로 판정하는 구조라 반드시
  `models.generate_batch`의 logit 기반 경로를 써야 한다는 걸 재확인(스모크를 `generate_batch`로
  다시 돌려서 확인).

**구현**: `models.py`에 `parse_response_harm()` 추가, `generate_batch()`에 `target="prompt"|"response"`
파라미터 추가(기본값 "prompt"라 eval.py는 영향 없음). `exp/response_harm.py`는 en/ko 각각
PGPrompts 전량을 3모델로 재실행하고, `prompt`/`response` 두 축 F1을 나란히 `harm_axis_summary.csv`에
기록하도록 작성.

**OOM 사고**: 1차 실행이 `polyguard/ko` 배치 144/1689 부근에서 `CUDA OutOfMemoryError`(25GB
할당 시도)로 중단. en 3모델(polyguard/llamaguard/sguard)은 이미 완료돼 CSV로 저장돼 있었음.
원인 조사: PGPrompts `response` 필드 토큰 길이를 확인해보니 ko에 **40,854 토큰짜리 극단
이상치**가 섞여 있었다(en은 최대 3,750). batch_size=16 동적 패딩에서 이 이상치가 낀 배치의
attention 메모리가 시퀀스 길이 제곱에 비례해 터진 것. p99가 en 1321 / ko 1965로 2048 밑이라
`models.py`의 `generate_batch` 토크나이즈 호출에 `truncation=True, max_length=2048`을 추가해
해결(영향받는 샘플 en 3건/ko 11건, 각각 1699건 중 <1%). `exp/response_harm.py`도 이미 끝난
model/lang 조합은 기존 CSV를 재사용하고 나머지만 이어서 돌리도록 재개 가능하게 수정, ko만
재실행해서 완료.

**결과** (`results/final/harm_axis_summary.csv`, PGPrompts en/ko 각 1689건):

| model | axis | en F1 | ko F1 |
|---|---|---|---|
| PolyGuard | prompt | 0.8729 | 0.8158 |
| PolyGuard | response | 0.7392 | 0.6333 |
| LG3-1B | prompt | 0.7478 | 0.5693 |
| LG3-1B | response | 0.4530 | 0.3669 |
| SGuard-v1 | prompt | 0.8877 | 0.7538 |
| SGuard-v1 | response | 0.7957 | 0.4748 |

parse 실패율은 전부 1% 미만(polyguard ko 0.89%, llamaguard ko 0.06%, 나머지 0%) — verify 기준
<5% 통과. 3모델 다 response 축이 prompt 축보다 F1이 낮다. LG3-1B가 response 축에서 가장 크게
무너진다(en 0.75→0.45, ko 0.57→0.37) — Agent 메시지 평가가 User 메시지 평가보다 근본적으로
어려운 과제일 가능성. SGuard도 ko에서 낙폭이 크다(0.75→0.47).

**다음**: EXP-3(confidence calibration) 착수 예정. logprob 재실행 여부는 계획서상 "재실행 없음"
전제인데, EXP-2에서 이미 한 번 그 전제가 깨졌으니 착수 전에 기존 예측에 logprob이 저장돼
있는지부터 확인할 것.

## EXP-3: Confidence Calibration (진행 중 — 데이터 재실행 단계)

**전제 확인**: NEW_PLAN.md는 "GPU 재실행 없음, Phase 7 confidence 추출을 기존 예측에 적용"을
전제하는데, `results/*.csv` 전부(prompt-harm, response-harm, ko_probe) 헤더를 확인한 결과
confidence/logprob 컬럼이 하나도 없었다. 원인은 `eval.py`가 호출하는 `generate_batch()`가
llamaguard/polyguard 배치 경로에서 `output_scores`를 아예 켜지 않고(sguard는 켜지만 확률 계산
후 라벨만 남기고 버림), confidence를 계산하는 코드(`moderate()`)는 `app.py` 실시간 서빙
단일-예제 경로에만 있고 배치 평가 파이프라인에 연결돼 있지 않았기 때문. 재실행이 필요하다는
점을 보고하고 승인받아 진행(NEW_PLAN.md가 요구하는 "비용 보고 후 진행 여부 확인" 절차).

**구현**: `models.py`의 `generate_batch()`를 확장 — `moderate()`에 있던 confidence 계산 로직
(safe/unsafe 혹은 yes/no 결정 토큰 두 후보만 뽑아 2-way softmax한 max 확률, sguard는 5카테고리
확률 중 triggered 카테고리 max 또는 전부 safe면 min)을 배치 버전으로 그대로 옮겨 반환값을
`(pred_labels, raw_outputs)` → `(pred_labels, raw_outputs, confidences)` 3-tuple로 변경.
`eval.py`의 `run_eval`/`run_eval_ko_probe` 둘 다 CSV에 `confidence` 컬럼 추가. `exp/response_harm.py`도
같은 함수를 쓰므로 언패킹만 맞춤(단, 이 스크립트는 `target="response"`라 polyguard 출력에서
"Harmful request" 줄이 먼저 나오는 구조상 첫 yes/no 토큰이 response가 아니라 prompt 축 confidence를
줍는다 — 부정확할 수 있어 이번엔 CSV에 confidence를 안 붙였다, `generate_batch` docstring에 기록).
기존 `results/{model}_{lang}.csv`를 덮어쓰지 않도록 `eval.py`에 `--tag` 옵션 추가.

**스모크 → 전체 sweep**: llamaguard/en n=20으로 먼저 검증하다가 `results/llamaguard_en.csv`(기존
465건 전체 결과)를 실수로 덮어썼다 — `git checkout`으로 즉시 복구. 이후 `--tag _conf`로 3모델×2언어
전체(`--n 1699`, PGPrompts 전량, Phase 6와 동일 표본)를 서버 백그라운드로 순차 실행, 전부 정상 완료
(OOM/파싱실패 없음). F1은 Phase 6 결과와 오차범위 내 일치(최대 0.6%p 차이, 배치 패딩 순서에 따른
부동소수 비결정성으로 추정 — 로직 변경 아님):

| model/lang | F1 (Phase6 → EXP-3 재실행) | confidence 평균 |
|---|---|---|
| llamaguard/en | 0.7478 → 0.7478 | 0.9067 |
| llamaguard/ko | 0.5693 → 0.5698 | 0.8813 |
| polyguard/en | 0.8729 → 0.8729 | 0.9797 |
| polyguard/ko | 0.8158 → 0.8158 | 0.9524 |
| sguard/en | 0.8877 → 0.8884 | 0.9738 |
| sguard/ko | 0.7538 → 0.7492 | 0.9253 |

산출물: `results/{model}_{lang}_conf.csv` 6개(confidence 컬럼 포함, null 0건, 범위 0.5~1.0 — 이진
softmax 최솟값이 0.5라 타당).

**남은 작업**: (1) `data/ko_probe.csv`(150행) confidence 포함 재실행 — 아직 안 함. (2) 10-bin
reliability diagram + ECE 계산, `results/final/calibration_{model}.csv`/`calibration_summary.csv`
산출 — 아직 안 함. (3) `figures/reliability_{model}.png` 생성, SGuard confidence 정의가 타 모델과
다르다는 점을 캡션에 명시 — 아직 안 함. 지금까지는 "GPU 재실행" 단계만 완료된 상태.

## EXP-3 이어서: ko_probe 재실행 사고 + calibration 분석 완료

**--tag 버그 발견**: `eval.py --model X --ko-probe --tag _conf`를 실행했더니 `run_eval_ko_probe`에
`tag` 파라미터가 애초에 없어서(PGPrompts용 `run_eval`에만 붙였던 걸 빠뜨림) `--tag`를 줘도 무시되고
`results/ko_probe_{model}.csv`(기존 파일, Phase 5 flip rate 표의 근거)를 그대로 덮어썼다. `git status`로
바로 발견해서 `git checkout`으로 즉시 복구, `run_eval_ko_probe`에도 `tag` 파라미터를 연결하는 수정을
커밋한 뒤 재실행 — 이번엔 `results/ko_probe_{model}_conf.csv`로 정상 분리 저장됐고 원본 3개 파일은
`git status`로 clean 확인. **패턴**: `eval.py`에 파라미터를 추가할 때 두 실행 경로(`run_eval`,
`run_eval_ko_probe`) 양쪽에 다 연결했는지 확인할 것 — 이번이 두 번째 실수(첫 번째는 스모크 테스트 중
`results/llamaguard_en.csv`를 덮어쓴 것).

**calibration 분석**: `exp/calibration.py` 작성 — PGPrompts en/ko 전량 + ko_probe 세 소스를 모델별로
합쳐(세 CSV 모두 `id/pred_label/true_label/confidence` 컬럼명이 동일해서 그대로 concat 가능)
`results/final/calibration_{model}.csv` 저장, confidence를 10-bin(0.5~1.0 균등)으로 나눠 bin별
(mean confidence, accuracy, n)과 ECE(bin별 |acc−conf|의 샘플 가중 평균)를 계산.

**폰트 이슈**: 첫 실행 시 reliability diagram 캡션에 넣은 한국어 텍스트가 matplotlib 경고
(`Glyph ... missing from font(s) DejaVu Sans`)와 함께 빈 사각형으로 렌더링됐다. 서버에
Hangul 폰트가 없음을 `fc-list`로 확인 — 폰트를 새로 설치하는 대신 캡션만 영어로 전환(CSV/문서는
그대로 한국어 유지)해서 해결.

**결과** (`results/final/calibration_summary.csv`):

| model | ECE | n | low-sample bins(n<30) |
|---|---|---|---|
| LG3-1B | 0.1614 | 3547 | 0 |
| PolyGuard | 0.1017 | 3548 | 1 |
| SGuard-v1 | 0.1065 | 3548 | 0 |

세 모델 reliability diagram을 직접 확인(`figures/reliability_*.png`) — 셋 다 accuracy per bin이
대각선(perfect calibration) 아래에 계속 위치해 **과신(overconfident) 경향이 뚜렷**하다. LG3-1B가
가장 심함(confidence 0.9대 bin에서 accuracy는 0.6~0.8대에 그침). LG3-1B는 n=1 parse 실패 제외.
