## EXP-1: Latency 벤치마크

`docs/NEW_PLAN.md`에 잔여 실험 5건(EXP-1~5)을 정리해뒀고, 그중 EXP-1(latency)부터 착수했다.
NEW_PLAN.md 자체도 아직 커밋 안 된 상태였어서 같이 커밋했다.

**설계**: ko_probe 원문(variant_type=="원문") 30문장 + PGPrompts en 20문장(`results/llamaguard_en.csv`
첫 20행, 기존 평가에서 쓴 데이터셋 순서 그대로 재사용) = 50건 고정 세트를 `exp/latency_inputs.json`에
저장. 모델당 warmup 5회(측정 제외) 후 batch=1로 순차 측정. `torch.cuda.synchronize()`를 tokenize/
generate 각 구간 전후에 호출해서 비동기 커널로 인한 왜곡을 막았다. 모델 전환 시 `del model` +
`torch.cuda.empty_cache()`.

**구현 이슈**: `python exp/latency_bench.py`로 실행하면 `sys.path[0]`이 `exp/`가 되어 루트의
`models.py`를 못 찾는다(`ModuleNotFoundError: No module named 'models'`). `PYTHONPATH=.`을 붙여서
해결 — 서버에서 이 스크립트를 다시 실행할 일이 있으면 반드시 `PYTHONPATH=. python exp/latency_bench.py`
형태로 실행할 것.

**결과** (`results/final/latency_raw.csv`, `latency_summary.csv`):

| model | median_ms | p95_ms | mean_output_tokens | ms_per_output_token |
|---|---|---|---|---|
| llamaguard | 46.6 | 89.4 | 3.18 | 15.5 |
| polyguard | 677.2 | 722.2 | 31.6 | 21.8 |
| sguard | 297.7 | 299.3 | 5.0 | 59.6 |

절대 latency는 LG3-1B가 압도적으로 빠르지만, 이는 출력 토큰 수가 짧기 때문(safe/unsafe 한 줄).
토큰당 정규화(`ms_per_output_token`)로 보면 SGuard가 가장 느리다(5토큰짜리 카테고리 생성인데도
스텝당 비용이 큼 — 2B 파라미터 규모 때문으로 추정, 별도 분석은 안 함). p95가 median 대비 크게
튀는 모델은 LG3-1B(46.6 → 89.4ms, 약 2배) — 일부 입력에서 unsafe 판정 시 카테고리 코드까지
생성하느라 출력 토큰 수가 늘어난 결과로 보인다(raw CSV의 output_len_tokens로 확인 가능).

## EXP-2: Response Harmfulness 재현

**계획 수정 발견**: NEW_PLAN.md는 "PolyGuard는 재실행 불필요, 기존 4-field raw 출력에서 파싱만
추가"라고 가정했는데, 기존 `results/polyguard_{lang}.csv`/`results/sguard_{lang}.csv`를 열어보니
전부 `response=""`로 실행된 것이었다(eval.py의 `run_eval`이 애초에 prompt만 넘김). 즉 기존
raw_output의 "Harmful response" 필드는 빈 응답에 대한 판정이라 이번 실험에 못 쓴다. 사용자에게
보고하고 3모델 전부 재실행으로 계획을 수정했다(승인받음).

**판단 근거 확보 (스모크 테스트)**:
- PGPrompts 데이터셋 필드 확인: `response`(실제 응답 텍스트), `response_harm_label`(정답,
  harmful/unharmful). en/ko 각 1699건(prompt_harm_label 있는 것) 중 `response_harm_label=None`
  10건 제외, 빈 문자열 response는 0건.
- LG3-1B: chat template에 user+assistant 두 턴을 넣으면 "Task: Check ... in 'Agent' messages"로
  자동 전환되는 걸 실제 출력으로 확인 — 별도 프롬프트 포맷 불필요, 기존 safe/unsafe 첫 줄 파서
  그대로 재사용 가능.
- PolyGuard: raw_output에 이미 "Harmful response: yes/no" 필드 있어 정규식 파서만 추가
  (`models.parse_response_harm`).
- SGuard: 모델 카드 예제(`{"role":"user","prompt":...,"response":...}`)가 `models.py`에 이미
  구현돼 있어 response만 채우면 됨. 단 일반 `tok.decode()`로 스모크했더니 빈 문자열이 나와서
  당황했는데, SGuard는 5개 카테고리를 special token logit 비교로 판정하는 구조라 반드시
  `models.generate_batch`의 logit 기반 경로를 써야 한다는 걸 재확인(스모크를 `generate_batch`로
  다시 돌려서 확인).

**구현**: `models.py`에 `parse_response_harm()` 추가, `generate_batch()`에 `target="prompt"|"response"`
파라미터 추가(기본값 "prompt"라 eval.py는 영향 없음). `exp/response_harm.py`는 en/ko 각각
PGPrompts 전량을 3모델로 재실행하고, `prompt`/`response` 두 축 F1을 나란히 `harm_axis_summary.csv`에
기록하도록 작성.

**OOM 사고**: 1차 실행이 `polyguard/ko` 배치 144/1689 부근에서 `CUDA OutOfMemoryError`(25GB
할당 시도)로 중단. en 3모델(polyguard/llamaguard/sguard)은 이미 완료돼 CSV로 저장돼 있었음.
원인 조사: PGPrompts `response` 필드 토큰 길이를 확인해보니 ko에 **40,854 토큰짜리 극단
이상치**가 섞여 있었다(en은 최대 3,750). batch_size=16 동적 패딩에서 이 이상치가 낀 배치의
attention 메모리가 시퀀스 길이 제곱에 비례해 터진 것. p99가 en 1321 / ko 1965로 2048 밑이라
`models.py`의 `generate_batch` 토크나이즈 호출에 `truncation=True, max_length=2048`을 추가해
해결(영향받는 샘플 en 3건/ko 11건, 각각 1699건 중 <1%). `exp/response_harm.py`도 이미 끝난
model/lang 조합은 기존 CSV를 재사용하고 나머지만 이어서 돌리도록 재개 가능하게 수정, ko만
재실행해서 완료.

**결과** (`results/final/harm_axis_summary.csv`, PGPrompts en/ko 각 1689건):

| model | axis | en F1 | ko F1 |
|---|---|---|---|
| PolyGuard | prompt | 0.8729 | 0.8158 |
| PolyGuard | response | 0.7392 | 0.6333 |
| LG3-1B | prompt | 0.7478 | 0.5693 |
| LG3-1B | response | 0.4530 | 0.3669 |
| SGuard-v1 | prompt | 0.8877 | 0.7538 |
| SGuard-v1 | response | 0.7957 | 0.4748 |

parse 실패율은 전부 1% 미만(polyguard ko 0.89%, llamaguard ko 0.06%, 나머지 0%) — verify 기준
<5% 통과. 3모델 다 response 축이 prompt 축보다 F1이 낮다. LG3-1B가 response 축에서 가장 크게
무너진다(en 0.75→0.45, ko 0.57→0.37) — Agent 메시지 평가가 User 메시지 평가보다 근본적으로
어려운 과제일 가능성. SGuard도 ko에서 낙폭이 크다(0.75→0.47).
